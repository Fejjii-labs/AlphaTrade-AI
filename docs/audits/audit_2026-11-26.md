# AlphaTrade repo and safety audit, 26 November 2026

Audited commit: `2b1f99c` (main). Brief: `docs/strategies/briefs/fable_audit_brief.md`.

This was a read-and-report audit. No production code was changed, nothing was deployed,
no orders were placed, no tests were run against any database, and no secret values were
read or printed. Every finding below was read in the code. Anything I could not confirm
(mostly what BloFin really returns, and what is set on staging) is marked **UNVERIFIED**.

## One-page summary

**Real money is safe.** Nothing in the code can reach a live BloFin host. The demo host
is checked on every single request, the live mode refuses to start, and the settings
refuse to load if the demo URL points at a production host. I found no gap here.

**The stop for stepped-exit trades is not yet as safe as the brief assumes.** The brief
says every open position must always have a stop that works when the worker is down.
For ordinary trades that is true: the stop and target are attached to the entry order.
For stepped-exit trades it is not always true, for four reasons:

1. **The bot only looks after the 20 oldest unfinished trade records each cycle, and
   records that never became trades stay in that list forever** (C-1). Once 20 of them
   pile up, newer open trades are never looked at again: no stop, no targets, no backup
   stop, no close detection. Nothing alerts. This is the one critical finding.
2. **A stepped-exit trade has no stop at all between the entry and the next cycle**
   (H-1). Usually that is well under a minute. If the worker dies in that window, the
   position has no stop until the worker is back.
3. **When placing the backup stop fails, nobody is told** (H-2). The brief says a failed
   placement "only alerts". In the code it only writes an INFO log line. There is no
   Telegram message, no counter and no kill switch.
4. **Several unrelated failures skip stop management entirely** (H-3, H-4, H-5): one
   unreadable BloFin read, one unexpected order state, or one exception in another
   trade's bookkeeping.

**The numbers shown for bot trades are not BloFin's numbers.** Bot trades are closed in
the journal with no profit or loss figure and the result left as "open" (H-7). The
dashboard win rate and realised P&L therefore leave out every bot trade, and the
per-strategy stats show 0 wins. The Telegram close page and weekly stats are computed
locally from prices, without funding.

**The tests that protect these paths mostly do not run on pull requests** (H-8). PR CI
picks tests by file name, and the exit proof, the backup stop and the BloFin client have
no name-matched test file. Tests that need Postgres are skipped on every PR. Main is
never tested after a merge.

**Suggested order of work**, one PR each: C-1, then H-2 (alerting, small), H-1, H-4,
H-5, H-8, H-6, H-7, H-9. The medium and low items can follow.

## Critical

### C-1. Reconciliation takes the 20 oldest unresolved commands, and dead ones never leave

- **Where:** `backend/src/app/services/governed_blofin_demo.py:2580-2626` (query,
  `.limit(20)` at 2624, oldest first at 2621-2623); early returns at 2169-2176;
  `backend/src/app/services/venue_submit_dispatcher.py:839` (sets the effect to
  `PROVEN_UNSENT` and leaves the command as `ALLOW`);
  `backend/src/app/services/demo_lifecycle_resolution.py:476` (the only place a
  resolution row is created, on a proven close).
- **What can go wrong:** the pending query keeps every allowed demo command that has no
  lifecycle resolution. A command refused before the order was sent, rejected by BloFin,
  cancelled unfilled, or left as an ambiguous operator hold never gets a resolution, so
  it is picked again every cycle and returns `demo_not_sent` or `demo_rejected`. Once 20
  such commands exist they fill the whole window. Every newer trade is then never
  reconciled: its fills are not recorded, a stepped-exit trade gets no stop close, no
  target close and no backup stop, a missing attached stop does not arm the kill switch,
  and a closed trade is never marked closed, which also blocks that coin for new entries.
- **How likely:** high over weeks. Demo data mode takes every valid setup, and refusals
  just before sending are common (they are the subject of #494 and #505). The count on
  staging today is UNVERIFIED.
- **Suggested fix:** leave out terminal states from the query (`PROVEN_UNSENT`,
  `REJECTED`, cancelled with no fills), or sort filled and open commands first. Log and
  alert when the pending count reaches the limit. Add a test with 25 dead commands and
  one open trade.

## High

### H-1. A stepped-exit trade has no stop between the entry and the next cycle

- **Where:** `backend/src/app/providers/exchange/governed_blofin.py:719-730` (stop and
  target are attached only when the plan is not a ladder);
  `backend/src/app/services/partial_exits/demo.py:293-301` (the backup stop is placed
  inside a manager step); `backend/src/app/services/governed_blofin_demo.py:2350` (the
  step runs only inside `reconcile_command`);
  `backend/src/app/workers/watcher_paper.py:730-733` (reconcile runs at the start of
  the next cycle).
- **What can go wrong:** the entry is sent during the scan part of a cycle. The first
  backup stop is placed at the start of the following cycle, after the 15 second poll
  and after older commands are reconciled. If the worker is killed in between (deploy,
  out of memory, crash), the position sits on BloFin with no stop until the worker
  returns. The first step also places no backup stop when a target is already reached
  (`not closes` at line 296) or when the entry is still partly open (2447-2448).
- **How likely:** the window is short, so low per trade, but a deploy or memory restart
  during it is realistic over months, and C-1, H-3, H-4 and H-5 all stretch the window
  without limit.
- **Suggested fix:** place the backup stop in the same cycle as the entry, straight
  after the fill is read, and treat a stepped-exit entry whose backup stop is not
  confirmed within N seconds as a protection failure (alert, then close). Longer term,
  ask whether BloFin accepts an attached stop only (no target) on a ladder entry, which
  would remove the window.

### H-2. A failed backup stop, and a failed step, are only log lines

- **Where:** `backend/src/app/services/partial_exits/demo.py:322-323` (returns the alert
  text `backup_stop_failed`); `backend/src/app/services/governed_blofin_demo.py:2492-2499`
  (the alerts are joined into one `logger.info` line and dropped); 2488-2491 (any
  exception in the step becomes `demo_ladder_unavailable` with a warning log).
- **What can go wrong:** the brief states that a failed placement alerts. Nothing reads
  these alerts: no Telegram message, no status row, no kill switch. A trade whose backup
  stop BloFin keeps rejecting, or whose step fails every cycle, looks healthy from
  outside while it has no working stop when the worker is down.
- **How likely:** certain whenever a placement fails.
- **Suggested fix:** send a Telegram alert on the first `backup_stop_failed`,
  `close_place_failed` or `demo_ladder_unavailable` for a trade, and page again if it
  repeats for more than a few cycles. Keep the "never blocks a close" rule.

### H-3. Unrelated failures skip stop management for a stepped-exit trade

- **Where:** `backend/src/app/services/governed_blofin_demo.py`, each of these returns
  before the ladder step at 2350:
  - 2183-2184: the entry read fails (`demo_reconciliation_unavailable`).
  - 2286-2299: the liquidation-price hold returns every cycle.
  - 2304-2315: a position that differs from the owned fills arms the kill switch and
    returns, every cycle, so the bot's own stop never runs for that trade again.
  - 2442-2443: the partial-exit flag is turned off while a ladder trade is open.
  - 2454-2456 and `partial_exits/demo.py:186-188`: the hold state cannot be read
    (`hold_state_unavailable`), so nothing is read or written, not even a crossed stop.
- **What can go wrong:** the bot is the only thing that closes a stepped-exit trade at
  its stop. In each case above it stops doing so, and it also stops placing or
  tightening the backup stop. If the backup stop was already resting, the trade is still
  covered at its last trigger. If it was not (H-1, H-2), there is no stop.
- **How likely:** each case is uncommon; together they are plausible, and BloFin read
  failures happen in bursts.
- **Suggested fix:** run the backup-stop check before the reads that can fail, and let a
  crossed stop close on a best-effort basis in every one of these branches. Refuse to
  load settings that turn the partial-exit flag off while a ladder trade is open, or
  alert on it.

### H-4. One exception in reconciliation stops the whole watcher cycle

- **Where:** `backend/src/app/workers/watcher_paper.py:730-733` (no try/except around
  the reconcile call); `backend/src/app/services/governed_blofin_demo.py:2642` (one
  generator over all commands, no isolation per command).
- **What can go wrong:** `reconcile_command` guards the BloFin calls but not the
  database work around them (fill projection, terminal recording, the closed-trade
  step). One command that raises every time fails the cycle before any scan and before
  any later trade is reconciled. It is retried first on every cycle because the order is
  oldest first. After five failures the supervisor also slows the loop
  (`backend/src/app/workers/paper_worker.py:1345-1359`).
- **How likely:** low to medium; the effect is that the bot stops trading and stops
  managing every open trade until someone steps in.
- **Suggested fix:** try/except per command with a reason code and an alert, and wrap
  the reconcile call so that scanning still runs.

### H-5. The order state `partially_canceled` is not handled on the trading path

- **Where:** `backend/src/app/providers/exchange/governed_blofin_partial_exits.py:47-54`
  and 128-130; `backend/src/app/providers/exchange/governed_blofin_exit.py:142` and 241;
  `backend/src/app/providers/exchange/demo_reconciliation.py:234-246`. The repo itself
  lists the state as a BloFin value in
  `backend/src/app/providers/exchange/blofin_activity.py:159`.
- **What can go wrong:** if one of the bot's closing orders ends partly filled and then
  cancelled, `closing_orders` raises "Unreadable demo closing order" on every cycle. The
  step then fails every cycle (H-2 means silently), so neither the stop nor the backup
  stop is managed. The exit proof raises "Unexplained demo account activity" for the
  same row, so the trade can never be proven closed and the coin stays blocked.
- **How likely:** low per order on liquid coins. Whether BloFin returns this state for a
  market order on the demo is UNVERIFIED.
- **Suggested fix:** treat `partially_canceled` as cancelled with fills in all three
  places and add tests for each.

### H-6. When the backup stop fires, a failed proof leaves the coin stuck with no alert

- **Where:** `backend/src/app/services/governed_blofin_demo.py:2316-2318` (any exception
  from the exit proof is swallowed with no log);
  `backend/src/app/services/partial_exits/demo.py:261-262` (the manager then reports
  `venue_position_mismatch` every cycle);
  `backend/src/app/services/partial_exits/demo_wiring.py:36-40` (that reason is not an
  operator hold, so no kill switch and no alert);
  `backend/src/app/providers/exchange/governed_blofin_exit.py:344-382` (the proof of a
  backup-stop close); 177-185 (any resting order on the coin means "still open").
- **What can go wrong:**
  - The proof for a fired backup stop was written against a made-up response
    (`backend/tests/test_ladder_backup_stop.py:214-258`). The module notes record that
    placing, following, amending and cancel-on-close were checked on the demo, not a
    triggered stop. If the real row differs (for example `actualSize` of `-1` or `0`,
    which `_positive` rejects, or a history endpoint that does not filter by
    `clientOrderId`), the proof raises every cycle. UNVERIFIED either way.
  - No code cancels the backup stop. If BloFin ever leaves it resting after the bot
    closes the position, the proof returns "still open" forever, and the entry check
    (`governed_blofin.py:419-430`) refuses new entries on that coin.
  - In both cases the trade stays open in the journal, the coin is blocked, the daily
    summary lists it as open, and nothing tells the operator.
- **How likely:** unknown until one real triggered stop is captured; the first real
  trigger is the test.
- **Suggested fix:** trigger one backup stop on the demo on purpose and save the cleaned
  responses as a fixture. Log the swallowed exception with its reason. Alert when a
  trade reports `venue_position_mismatch` or an unproven flat position for more than a
  few minutes. Cancel a backup stop that is still resting after the position is flat.

### H-7. Bot trades are closed in the journal with no P&L, so headline figures are wrong

- **Where:** `backend/src/app/services/demo_lifecycle_resolution.py:346-351` (`gross_pnl`,
  `funding`, `net_pnl` set to None and `result` to OPEN on close);
  `backend/src/app/services/blofin_demo_manual_mirror.py:1865-1867` (the mirror, which
  carries BloFin's own `realizedPnl`, skips bot trades) and 2257-2266 (dashboard totals
  read mirror rows only);
  `backend/src/app/services/autonomous_strategy_stats.py:113-115` and 208-210;
  `frontend/src/components/dashboard/BloFinDemoAccountCard.tsx:139-157`.
- **What can go wrong:** the brief expects the journal to use BloFin's figures. For bot
  trades the journal holds none. The trade page shows a dash for net P&L and the result
  as open. The dashboard "Win rate" and "Realized PnL" cover hand-placed trades only,
  next to an account equity that includes the bot. The per-strategy stats count bot
  trades as closed with zero wins and show missing P&L as $0.00.
- **How likely:** certain, on every bot trade.
- **Suggested fix:** when the mirror meets a closed position that belongs to a bot
  trade, write BloFin's `realizedPnl`, fee and funding onto that trade's journal row,
  matched by the order ids the exit proof already holds, and set the result from the
  sign. Until then, label the dashboard card "hand-placed trades only", and use decided
  trades as the win-rate denominator.

### H-8. Pull-request CI does not run the tests that protect these paths

- **Where:** `.github/workflows/ci.yml:110-120` (PRs run only
  `scripts/run_backend_focused.py`, with `CI: "false"` at line 114);
  `scripts/run_backend_focused.py:71-76` (tests are chosen by matching the changed file
  name); `.github/workflows/ci.yml:3-11` and 122-124 (the full suite runs only on a
  manual dispatch; there is no `push` trigger).
- **What can go wrong:**
  - No name-matched test exists for `governed_blofin_exit.py`,
    `governed_blofin_partial_exits.py`, `blofin_client.py`, `daily_risk_accounting.py`
    or `partial_exits/demo_wiring.py`. A change to `partial_exits/demo.py` selects
    unrelated `test_demo_*.py` files and not `test_partial_exit_demo.py`. A PR that
    changes the exit proof or the backup stop can pass with none of its tests run.
  - With `CI: "false"`, every Postgres-gated test is skipped on PRs: all of
    `backend/tests/test_governed_demo_lifecycle.py`, the worker-restart tests in
    `backend/tests/test_governed_blofin_demo.py`, the per-coin concurrency cases, and 16
    of 17 migration tests, while Render runs the migrations before each deploy
    (`render.yaml:14`).
  - Main is never tested after a merge.
- **How likely:** high. It depends only on which files a PR touches.
- **Suggested fix:** add an explicit map from safety source files to their test files in
  the selector (the script already does this for SFP). Add a Postgres service to the PR
  job for a small safety and migration subset. Run the full gate on push to main or
  nightly. The repo rule against `workflow_dispatch` stays as it is.

### H-9. The scan cap drops the same strategies every cycle

- **Where:** `backend/src/app/workers/watcher_paper_targets.py:297-310` and 344-359;
  `backend/src/app/services/watcher_assignment_service.py:416-431`.
- **What can go wrong:** the fair-share cut from #518 takes one scope per coin in turn,
  always in the same order (strategy creation time). There is no rotation. With more
  enabled scopes than the cap, each coin keeps its oldest strategies and its newest are
  never scanned at all. The only signal is a warning log on every target load. The
  explicit-assignment path is still a plain cut in coin order.
- **How likely:** certain whenever enabled scopes exceed the cap; the #518 message cites
  80 against 50 on staging. Which strategies lose out there is UNVERIFIED.
- **Suggested fix:** rotate the cut each cycle, or scan first the scopes whose candle
  just closed. Show dropped scopes in the runtime status and alert once. Raising the cap
  is cheap, because candles are cached per coin and timeframe.

## Medium

### M-1. The backup stop is off by default and nothing ties it to stepped exits

- **Where:** `backend/src/app/core/config.py:352-357`; 888-892 (the strict true/false
  check covers the two partial-exit flags, not this one); `.env.example:216`.
- **What can go wrong:** a new environment, or a staging variable lost in a redeploy,
  runs stepped exits with no exchange stop at all, with no warning at startup.
- **How likely:** low on staging today, likely on any new environment.
- **Suggested fix:** refuse to load settings with ladder families set and the backup
  stop off, unless a clearly named override is set. Add the flag to the strict check.

### M-2. The bot's stop and BloFin's stop can both fire; safe, but untested and noisy

- **Where:** `backend/src/app/services/partial_exits/demo.py:273-277` and 357-371;
  `backend/src/app/providers/exchange/governed_blofin_partial_exits.py:231-246`.
- **What can go wrong:** both closes are reduce-only, so the position cannot flip and I
  found no double-close that opens exposure. If BloFin closes first, the bot's close is
  rejected (`close_place_failed`, log only) and the manager reports a mismatch until the
  proof lands (H-6). The case where each closes part of the remainder has no test. The
  stop order does not set a trigger price type, while the bot compares against the last
  traded price; which price BloFin uses by default is UNVERIFIED.
- **How likely:** the race will happen on most stop-outs once both are active.
- **Suggested fix:** add tests for both orders of the race and for a split close. Set
  the trigger price type explicitly to match the bot.

### M-3. Order-history limits in the exit proof can leave a trade unprovable

- **Where:** `backend/src/app/providers/exchange/governed_blofin_exit.py:186-199`
  (history from the plan's start, no end, no paging, more than 20 rows raises);
  `backend/src/app/providers/exchange/governed_blofin.py:156-164` (100 rows or more
  raises).
- **What can go wrong:** any other order on the same coin after the plan's start time
  (a hand-placed demo order, or a previous trade's close if a plan can be created while
  that trade is still open, which is UNVERIFIED) makes the proof raise every cycle. It
  fails closed, so no trade is credited with another trade's fills, but the coin stays
  blocked (see H-6 for the missing alert).
- **How likely:** low to medium on an account that is also used by hand.
- **Suggested fix:** bound the history read by the entry's order time, page it, and
  alert on a persistent raise.

### M-4. Shutdown does not interrupt a cycle, and the watchdog exit can hang

- **Where:** `backend/src/app/workers/paper_worker.py:404-417`, 581-590, 1075-1079;
  `backend/src/app/workers/watcher_paper.py:764-783`.
- **What can go wrong:** after SIGTERM the running cycle scans every remaining scope and
  can still open a new order. Sleeps inside the cycle (up to 60 seconds) are not
  interruptible. If the cycle outlasts the 45 second stop budget, the leases are not
  released, and the next instance waits in standby, which reads as a rate-limit pause.
  On a memory-watchdog exit a stuck thread keeps the process alive with everything else
  stopped.
- **How likely:** some effect on most deploys that land during a busy cycle.
- **Suggested fix:** check the stop event between scopes and before any order, pass it
  into the sleepers, and force the exit after the join budget on the watchdog path.

### M-5. Binance budget waits block the single watcher thread; only a ban is alerted

- **Where:** `backend/src/app/market_contracts/adapters/request_budget.py:113-143`;
  `backend/src/app/market_contracts/adapters/binance_rest_gate.py:159-164` and 239-242;
  `backend/src/app/services/market_ban_visibility.py:58-63`.
- **What can go wrong:** one request budget is shared by all worker clients. When it is
  full, a request sleeps up to 60 seconds inside the scan and then fails as
  `rate_limited`. The trade-tape polling (weight 20 per page per coin every 10 seconds)
  uses far more budget than candles do. `rate_limited` can come from the budget, the
  soft weight limit, the startup standby, or a real 429. Which one produced the 30m
  observation is UNVERIFIED; I found nothing specific to 30m. The bot fails closed: it
  does not trade on stale candles. A long starved period only logs.
- **How likely:** recurring under load and after restarts.
- **Suggested fix:** give candles priority or their own budget, fail fast in the scan
  thread, and alert when a scope stays `rate_limited` for more than a few minutes.
  Stepped-exit management shares this thread, so this also widens H-1.

### M-6. Retention is off and dry-run by default, and several growing tables are outside it

- **Where:** `backend/src/app/core/config.py:368-369`;
  `backend/src/app/workers/paper_worker.py:950`;
  `backend/src/app/services/db_retention.py:239-403`.
- **What can go wrong:** without retention, the watcher event and scan tables, market
  observations and demo snapshots (about 1,900 rows a day) grow without limit. Even when
  on, `model_call_attempts`, `usage_events`, `risk_events`, `position_exit_events` and a
  few others have no policy. The staging values are UNVERIFIED.
- **How likely:** certain growth; the pain arrives over months.
- **Suggested fix:** turn retention on in staging (dry-run first), add policies for the
  uncovered tables, and alert when a pass is incomplete.

### M-7. No database connect, statement or lock timeouts

- **Where:** `backend/src/app/db/session.py:23-27` and 44-55.
- **What can go wrong:** a dropped connection or a lock wait during database maintenance
  can block a worker thread for good. The supervisor has no stuck-thread detection.
- **How likely:** low per day, realistic over months.
- **Suggested fix:** set a connect timeout, statement timeout, lock timeout and
  idle-in-transaction timeout, with a longer statement timeout for retention.

### M-8. `audit_logs` has no index for a query that runs every cycle

- **Where:** `backend/src/app/db/models.py:3530-3532`;
  `backend/src/app/services/governed_blofin_demo.py:2529-2537` and 2598-2609.
- **What can go wrong:** every cycle runs a lookup on organisation, resource type,
  resource id and a JSON field against a table whose only index is the event time. It
  gets slower as the table grows.
- **How likely:** certain, gradual.
- **Suggested fix:** add an index on resource type and resource id, and stop
  re-checking closed trades once their sample is admitted.

### M-9. Worker liveness is only checked when someone asks, and a failing worker looks fresh

- **Where:** `backend/src/app/services/worker_heartbeat.py:170-193`;
  `backend/src/app/api/routes/health.py:248`;
  `backend/src/app/workers/paper_worker.py:722-735`.
- **What can go wrong:** the stale-worker alert fires only when the health route is
  called, and the repo defines no scheduled caller. Whether an outside uptime monitor
  exists is UNVERIFIED. A cycle that raises still publishes a heartbeat, so H-4 never
  looks stale.
- **How likely:** matters every time the worker fails quietly.
- **Suggested fix:** schedule the check, and treat several failed heartbeats in a row as
  unhealthy and send an alert.

### M-10. A close recorded after the daily summary is sent never appears in any summary

- **Where:** `backend/src/app/services/demo_daily_summary.py:273` and 130-131;
  `backend/src/app/services/demo_lifecycle_resolution.py:303`.
- **What can go wrong:** summaries select by the venue fill time. A trade stopped at
  23:50 UTC and proven at 00:20 shows as "still open" for its day and is left out of the
  next day. On a Sunday it drops out of both weeks.
- **How likely:** moderate; it is exactly the backup-stop and held-exit case.
- **Suggested fix:** add a "closed earlier, recorded since the last summary" section
  keyed on when the close was recorded.

### M-11. The daily loss budget assumes fees are positive when paid

- **Where:** `backend/src/app/services/demo_lifecycle_resolution.py:99` and 431-432;
  `backend/src/app/services/blofin_demo_manual_mirror.py:11-13`.
- **What can go wrong:** the mirror's own notes record that the demo reports a paid fee
  as a negative number. If the fills endpoint does the same, the day's loss is
  understated by twice the round-trip fee on each losing trade, and bot rows carry the
  opposite fee sign to mirror rows. The real sign on the fills endpoint is UNVERIFIED;
  the test fixtures use both.
- **How likely:** unknown until checked against one real fill.
- **Suggested fix:** convert fees to a cost with one documented rule before any sum.

### M-12. The daily loss budget is not the day's P&L and matches no displayed figure

- **Where:** `backend/src/app/services/demo_lifecycle_resolution.py:420-436`;
  `backend/src/app/services/risk/daily_risk_accounting.py:199`.
- **What can go wrong:** the budget counts losses only (winners do not offset, which is
  cautious and looks deliberate), leaves out funding, and charges a stop filled at 23:59
  UTC and proven after midnight to neither day. The second accounting sums journal net
  P&L, which is empty for bot trades (H-7), so its "locked" display never reflects demo
  losses. It also uses the user's timezone where the demo ledger uses UTC.
- **How likely:** certain as a mismatch; the lock itself errs on the safe side except
  for the midnight case.
- **Suggested fix:** one helper for "the day's realised P&L", charge a late-proven loss
  to the day it is recorded, and document that the budget is gross losses.

### M-13. No recorded BloFin responses; the fakes never matched the real API

- **Where:** `backend/tests/fixtures/blofin_demo_manual_mirror.json:2` (states it is
  synthetic); `backend/tests/test_ladder_backup_stop.py:155-156` and 214-258;
  `backend/src/app/providers/exchange/blofin_account.py:32-34`;
  `backend/tests/test_exchange_blackbox.py:99-121`.
- **What can go wrong:** the governed tests replace the client and return the inner

## Checked and found sound

**Real-money guards (brief item 3).**
- `backend/src/app/providers/exchange/blofin_client.py:112` and 198: the demo host is
  asserted when the client is built and again on every request, and an absolute URL as a
  path is refused.
- `backend/src/app/core/exchange_safety.py:73-85`: live mode refuses to start, and a
  production host in the demo URL refuses to load in every mode.
- `backend/src/app/core/exchange_safety.py:93-99`: demo mode requires paper execution
  and real trading off.
- Every order-sending call goes through that client. The partial-exit and backup-stop
  calls check the demo host again
  (`backend/src/app/providers/exchange/governed_blofin_partial_exits.py:264-269` and
  293-300), and the partial-exit flag is false whenever a real-trading switch is on
  (`backend/src/app/services/partial_exits/flags.py:18-28`).
- I found no other exchange client that can send an order.

**Kill switch, loss lock, one position per coin (brief item 2).**
- The kill switch read fails closed, and reconciliation keeps running while it is on.
- A new entry needs the coin flat with no resting order or stop
  (`backend/src/app/providers/exchange/governed_blofin.py:392-430`) and no unresolved
  earlier entry on that coin
  (`backend/src/app/services/governed_blofin_demo.py:866-874`). That is why the failures
  above end in "stuck", not in a second position.
- The kill switch, worker pause and loss lock block target closes only; a crossed stop
  still closes (`backend/src/app/services/partial_exits/demo.py:76-78`).

**Order sending and the exit proof.**
- The "send may have happened" marker is committed before the order is posted, posts are
  never retried, and recovery reads by client order id.
- The backup-stop proof rejects a looser trigger, a foreign client id, a size mismatch,
  duplicates, a non-reduce-only order and a take-profit close.
- Client ids for closes are derived from the command id, so a restart reuses the id of a
  close that was never accepted.

**Money arithmetic.** Decimal throughout, correct signs for shorts, exit price weighted
over all closing fills, and R always measured against the original stop and full size.

**Worker.** HTTP timeouts on every outside call, bounded caches, per-scan exception
isolation, and no model calls in the scan loop.
